# Security review and patches, 28 July 2026

Host: `jwm-server` (Ubuntu 22.04, origin `194.195.211.175`)
Site: jerrywestonmize.com, WordPress 7.0.2 behind Cloudflare
Trigger: check whether anyone had gained remote access to the server

## Outcome

No one had gained remote access. The checks below all came back clean:

- Login records (`last`, `lastlog`, `who`) show only `huntaj` from known IPs. `jwmmail` last logged in during 2023, `jerrywestonmize` during 2024. Root has never logged in over SSH.
- `btmp` holds seven failed logins, all from 97.89.129.123, all attempts at the username `austinjhunt` instead of `huntaj`.
- One UID 0 account. `/etc/passwd`, `/etc/shadow`, and `/etc/group` unchanged since May 2024.
- No cron or systemd persistence. All user crontabs empty, `/etc/cron.d` and `cron.daily` stock.
- Listening ports limited to 22, 25, 80, 110, 143, 443, 993, 995, plus MySQL and OpenDKIM on localhost.
- No processes running from `/tmp`, `/dev/shm`, or `/var/tmp`. No deleted-binary processes.
- 14 SUID binaries, all standard. Recent mtimes trace to apt upgrades.
- Webroot git tree clean against `origin/main`.
- No webshells in uploads. The 41 PHP files there are `index.php` blockers plus one plugin define.

One anomaly turned out to be benign. At 05:38:35 EDT a client via Tor (Cloudflare country code `T1`) completed `POST /wp-login.php?action=register` and got a 302. That created the account `Geraldmip` with role `customer`, which is the site's configured `default_role` under intentionally open registration. Five requests total, no follow-up activity. The signature reads as a spam signup bot: generated username, mismatched email, Tor exit.

`wp-login.php` was reachable at the time because the WordPress 7.0.2 core update on 26 July restored the file that site hardening had removed.

## Changes applied

### Real client IPs in access logs

The `cloudflare` LogFormat in `apache2.conf` used `%{CF_CONNECTING_IP}i` with underscores. The header is `CF-Connecting-IP` with hyphens, so the field never matched and logged a bare dash for as long as the format existed. Every request appeared to come from a Cloudflare edge address.

- Enabled `mod_remoteip`.
- Added `/etc/apache2/conf-available/cloudflare-remoteip.conf` with `RemoteIPHeader CF-Connecting-IP` and Cloudflare's 15 IPv4 and 7 IPv6 ranges as `RemoteIPTrustedProxy` entries.
- Rewrote the format (line 220, old version commented at 218):

```apache
LogFormat "%v %a [Country:%{CF-IPCountry}i] (via cloudflare:%{c}a) %l %u %t \"%r\" %>s %b" cloudflare
```

`mod_remoteip` only honours the header from trusted ranges, so a direct-to-origin client cannot forge an address into the logs.

### Blocked web access to .git

`/.git/config`, `/.git/HEAD`, and `/.git/index` all returned 200 over HTTPS, which made the repository dumpable with standard tooling. Three scanners fetched `/.git/config` during the observed window (65.49.1.142, 158.94.208.120, 20.201.77.247).

This mattered more than a typical `.git` leak because `jwmsecure.php` is tracked here, so a dump would have disclosed the site's only working login path.

Added `/etc/apache2/conf-available/deny-vcs.conf`:

```apache
<DirectoryMatch "/\.(git|svn|hg|bzr)">
    Require all denied
</DirectoryMatch>
RedirectMatch 404 "/\.(git|svn|hg|bzr)(/|$)"
```

All three paths now return 404. Database credentials were never at risk: `wp-config.php` is excluded by the `/wp-*.php` gitignore rule and has never been committed.

### Restricted origin to Cloudflare

Roughly 17 percent of requests in the observed window bypassed Cloudflare and hit the origin directly, which made the Cloudflare WAF and rate limiting skippable. Most were commodity scanners probing paths like `/.env`, `/Orion/Login.aspx`, and `/RASHTML5Gateway/`.

Ports 80 and 443 now accept Cloudflare ranges only. SSH and the mail ports stay open to everyone, since Cloudflare does not proxy SMTP, IMAP, or POP3.

WordPress loopback requests still work because the server resolves `jerrywestonmize.com` to Cloudflare, so self-requests hairpin through the edge and arrive from a trusted range. Requests to the server's own public IP route over `lo` and never reach the external interface.

### Other

- `wp-config.php` permissions changed from 644 to 640, owner `www-data`. PHP runs as `www-data` under mod_php with no FPM pool or suexec, so the owner keeps read and write. `huntaj` retains read through group membership.
- Removed `SetEnv AMELIA_API_KEY` from `jerrywestonmize-le-ssl.conf`. Nothing on the host read it. The value should be rotated, since it sat in a world-readable file.
- `PasswordAuthentication no` in `sshd_config`, applied and confirmed refused. `/etc/ssh/sshd_config.d/` is empty, so no cloud-init drop-in can re-enable it.
- Deleted the `Geraldmip` customer account and the `Amelia Support` administrator account.

## Open items

`jwmsecure.php` is a static copy of `wp-login.php` served through an `Alias`. Core updates patch the original and never touch this fork, so it stays pinned to whatever version it was copied from. If a login-path vulnerability is published, this file remains affected. Replacing it with stock `wp-login.php` behind real access control is the durable fix.

Note that any access control on `wp-login.php` needs checking against Amelia first, since customer logins may post there. Gating it without checking would lock out the customer accounts.

Basic auth in front of the login was considered and declined. The site already runs limit-login-attempts-reloaded and Wordfence login security, and the origin now only accepts Cloudflare traffic.

Cloudflare rotates its published IP ranges. When they change, both `cloudflare-remoteip.conf` and the firewall rules will start rejecting legitimate edge traffic. These need periodic regeneration.

`auth.log` and `lastb` history older than 8 July was not reviewed. `btmp` begins 8 July and the readable `auth.log` begins 26 July, so the failed-login picture covers about three weeks.
